# Aster SVG 0.2.0

Status: **Published on 26 October 2026 (UTC)**.

Source commit: `b33ebef3dd44103bb6e346f8aa419326df1aea9a`.

Registry: [`@luscious-garden/aster-svg@0.2.0`](https://www.npmjs.com/package/@luscious-garden/aster-svg/v/0.2.0)

Approved archive SHA-256: `bafb7bfcd6254ea922214f0d1e434878ddb06df3102f46cf4ae8e455ed37f1a2`.

This version renders explicitly treated Core definitions through the existing `Svg.render()` API.
It hardens optional rendering data and reduces temporary option/point-serialisation work without
changing the supported rendering options or standalone SVG contract.

- Breaking change: require Core `^0.2.0`, whose definition contract requires `identity.variant`.
  Legacy definitions without a treatment are no longer accepted, even though the renderer's
  method name and parameter structure are unchanged.
- Compatible correction: prevent inherited optional option, policy and rectangle fields from
  supplying rendering values that the accepted data does not own.
- Compatible correction: reduce temporary work during option capture and point serialisation;
  recognised Core definitions are reused rather than rebuilt during rendering.

Requires Core `^0.2.0`. Icons is not a runtime dependency of the renderer.

## Migration

Apply the [Core migration](../../core/releases/0.2.0.md#migration) to definitions you author.
For Aster artwork, apply the [Icons import migration](../../icons/releases/0.3.0.md#migration),
then pass `CameraOutline` or `CameraVariants.outline` to `Svg.render()`, not `CameraVariants`
itself. There is no implicit treatment selection.

Keep existing render-option names. Retain one canonical definition for repeated renders instead
of calling `Icon.define()` on the same mutable data for every call. The
[rendering guide](../workflow.md) and
[definition-reuse guide](../../core/definition/runtime/index.md#reusing-definitions) own current
behaviour and its validation boundary.
